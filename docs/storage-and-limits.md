# Стратегия хранения данных и лимитов

## Назначение

Приложение будет позволять пользователям загружать семейные материалы: фотографии, голосовые записи, а в будущем, возможно, документы и видео. Такие файлы быстро становятся основной статьёй расходов, поэтому лимиты хранения и платное расширение нужно предусмотреть с самого начала.

## Текущие ресурсы

Сейчас приложение в Timeweb App Platform имеет:

- React frontend;
- 2 ГБ NVMe;
- публичный домен приложения;
- лимит входящих запросов не установлен.

Этого достаточно для кода приложения, MVP, демонстрации и небольшого тестового объёма данных. Для реального хранения пользовательских фото и голосовых записей этого недостаточно.

## Рекомендуемая модель хранения

Данные нужно разделить на два уровня:

- PostgreSQL или другая реляционная база данных для пользователей, семей, историй, прав доступа, метаданных, записей о файлах, тарифов и счётчиков занятого места.
- S3-совместимое объектное хранилище для фотографий, аудио, аватаров, документов, миниатюр и других тяжёлых файлов.

Файлы не нужно хранить напрямую в базе данных. В базе должны лежать метаданные файла и ключ/ссылка на объект в хранилище.

## Лимиты для пользователей и семей

Лимит лучше считать не на отдельного пользователя, а на семейный архив. Это понятнее для пользователя и лучше соответствует идее продукта.

Возможная модель:

- бесплатный архив: 100-300 МБ на семью;
- базовый платный архив: 2 ГБ;
- расширенный архив: 10 ГБ;
- большой архив: 50 ГБ или больше.

При достижении лимита приложение не должно сразу удалять данные. Лучше заранее предупреждать пользователей, при необходимости ограничивать новые загрузки и предлагать платное расширение.

## Контроль расходов

Чтобы хранение оставалось управляемым по цене:

- сжимать загруженные фотографии в WebP или AVIF;
- хранить голос в сжатых форматах, например AAC, M4A или Opus;
- создавать миниатюры для быстрой ленты;
- хранить оригиналы только на платных тарифах или не хранить их вообще;
- считать общий объём хранения по каждой семье;
- отдельно учитывать исходящий трафик;
- в будущем рассмотреть холодное хранение для редко открываемых материалов.

## Приватность

Семейные материалы не должны лежать в публичном бакете. Пользовательские файлы нужно хранить приватно, а доступ выдавать через авторизованные запросы приложения или временные подписанные ссылки.

## Предварительное решение

Для MVP можно начать с небольшого S3-совместимого хранилища и строгих лимитов. Архитектуру при этом нужно сразу проектировать так, будто в будущем объём данных может вырасти до нескольких терабайт.

Рекомендуемая долгосрочная архитектура:

- frontend: статический хостинг или App Platform;
- backend/API: отдельный сервис для авторизации, загрузок, прав доступа и бизнес-логики;
- база данных: PostgreSQL для структурированных данных;
- медиафайлы: приватное S3-совместимое хранилище;
- биллинг и лимиты: на уровне семейного архива.
